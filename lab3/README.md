# Лабораторная 3 — роли, временные ключи и защита доступа

Приложение из лабораторной 2 (SPA + REST API + MongoDB в Docker), дополненное
пятью пунктами задания.

## Что рассказать преподавателю (кратко, простыми словами)

**1. Роли.** В системе три вида пользователей. Обычный видит и меняет только
свои задачи. Менеджер видит и меняет все задачи, но удалять чужие не может —
только свои. Администратор может всё, включая удаление чужих задач и смену
ролей другим людям. Права проверяются на каждый запрос заново — сервер
каждый раз смотрит в базу, какая роль у человека прямо сейчас, а не запоминает
её один раз при входе. Поэтому если админ поменял кому-то роль, у того права
меняются сразу же, без повторного входа.
Код: кто что видит — [tasks.js:49-57](src/tasks.js#L49-L57) и
[tasks.js:139](src/tasks.js#L139); роль читается из базы —
[auth.js:140](src/auth.js#L140); запрет менять роль себе —
[admin.js:29-32](src/admin.js#L29-L32).

**2. Вход по ключам, а не по паролю каждый раз.** Пароль вводится один раз,
при входе. В ответ сервер выдаёт два ключа: короткий (действует 15 минут) —
браузер прикладывает его к каждому действию, и длинный (действует 7 дней) —
по нему можно получить новый короткий ключ, когда старый истёк. Так пароль
почти нигде не «путешествует» по сети лишний раз.
Код: короткий ключ создаётся в [auth.js:59-64](src/auth.js#L59-L64),
длинный — в [auth.js:69](src/auth.js#L69); проверка ключа на каждый
запрос — [auth.js:114-146](src/auth.js#L114-L146); автообновление на
клиенте — [app.js:93-107](public/js/app.js#L93-L107).

**3. Коды ответа сервера.** Сервер не просто говорит «ошибка», а отвечает
конкретным числом по общепринятому стандарту: 401 — не вошёл в систему,
403 — вошёл, но это действие не разрешено, 404 — такой записи нет, 409 — уже
существует (например, почта занята), 429 — слишком много попыток подряд.
Это позволяет любой программе, которая обращается к серверу, понимать ответ
без чтения текста ошибки.
Код: все коды собраны в обработчике ошибок [server.js:73-92](src/server.js#L73-L92)
и в заголовке файла [server.js:11-14](src/server.js#L11-L14); полная таблица
кодов — в разделе «Как сделаны пункты задания» ниже.

**4. Защита от подбора пароля.** Если пять раз подряд ввести неправильный
пароль, вход блокируется на 15 минут — причём даже шестая попытка с
правильным паролем в это время не пройдёт. Это защита от программы, которая
пытается перебрать пароли автоматически.
Код: счётчик промахов — [auth.js:219-231](src/auth.js#L219-L231); сама
проверка блокировки при входе — [auth.js:195-203](src/auth.js#L195-L203).

**5. Подключения.** Каждый успешный вход — это отдельная запись
«подключение» в базе, с адресом и временем. Одновременно у одного человека
разрешено не больше трёх — при новом входе самое старое закрывается само.
Свои подключения можно посмотреть и закрыть вручную — например, если забыл
выйти на чужом компьютере.
Код: создание подключения и лимит на три — [auth.js:68-91](src/auth.js#L68-L91);
свой список и закрытие — [auth.js:282-311](src/auth.js#L282-L311); то же
самое для администратора над чужими — [admin.js:45-69](src/admin.js#L45-L69).

**6. Восстановление пароля по почте.** Если забыл пароль — можно запросить
ссылку на почту. Ссылка одноразовая и живёт 30 минут. После смены пароля все
прежние подключения закрываются — чтобы старый ключ, который мог украсть
кто-то другой, тоже перестал работать.
Код: запрос ссылки и письмо — [auth.js:315-334](src/auth.js#L315-L334) и
[mail.js](src/mail.js); смена пароля по ссылке — [auth.js:337-359](src/auth.js#L337-L359).

**7. Структурированные логи.** Все важные события (вход, отказ в доступе,
ошибка) записываются не обычным текстом, а в виде мини-записей с одинаковыми
полями (JSON) — по ним удобно потом искать конкретное событие командой, а не
читать весь файл глазами.
Код: настройка лога — [logger.js:11-15](src/logger.js#L11-L15); запись на
каждый HTTP-запрос — [logger.js:21-40](src/logger.js#L21-L40), подключена
в [server.js:51](src/server.js#L51).

**8. Автоматическая проверка кода.** При каждом изменении кода на GitHub сама
запускается проверка (линтер) — ищет явные ошибки и нарушения стиля в коде.
Если что-то не так, это сразу видно на странице репозитория, без ручного
запуска проверки.
Код: правила проверки — [eslint.config.js](eslint.config.js); что и когда
запускается на GitHub — [.github/workflows/lab3.yml](../.github/workflows/lab3.yml).

## Запуск

```
docker compose up --build      ->   http://localhost:3000
```

Первый администратор создаётся при старте: `admin@lab3.local` / `admin12345`
(меняется переменными `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `docker-compose.yml`).
Все остальные регистрируются сами и получают роль `user`.

## Как сделаны пункты задания

### 1. Три роли на временных ключах

Ключей два, оба временные (`src/auth.js`):

| Ключ      | Что это                         | Срок    | Где хранится                        |
|-----------|---------------------------------|---------|-------------------------------------|
| `access`  | JWT, подписанный `JWT_SECRET`   | 15 мин  | нигде: подпись сама себя доказывает |
| `refresh` | случайная строка на 32 байта    | 7 дней  | коллекция `sessions` (только хеш)   |

Клиент кладёт `access` в заголовок `Authorization: Bearer ...`. Когда он
истекает, сервер отвечает `401` с полем `expired`, и скрипт сам меняет ключ
через `POST /api/auth/refresh` и повторяет запрос.

Роли и права (`src/tasks.js`, `src/admin.js`):

| Роль      | Задачи                          | Раздел «Пользователи»       |
|-----------|---------------------------------|-----------------------------|
| `user`    | видит и меняет только свои      | нет                         |
| `manager` | видит и меняет все, удаляет свои| нет                         |
| `admin`   | всё, включая удаление чужих     | роли и любые подключения    |

### 2. Коды возврата по семантике HTTP

`200` ok · `201` создано · `202` принято (письмо) · `204` без тела ·
`400` тело не разобрано · `401` нет входа (+ `WWW-Authenticate`) ·
`403` прав не хватает · `404` нет адреса или записи · `409` конфликт
(занятая почта) · `410` ссылка устарела · `413` файл больше 10 МБ ·
`422` данные не прошли проверку · `429` слишком много попыток
(+ `Retry-After`) · `500` ошибка сервера.

### 3. Защита доступа

- **Подбор пароля**: счётчик неудач по адресу в коллекции `attempts`;
  5 промахов подряд — вход блокируется на 15 минут, ответ `429`.
- **Активные подключения**: одна запись в `sessions` = один вход.
  Больше трёх одновременно не держим — самое старое закрывается.
  Свои подключения видны на экране «Подключения», все — у администратора.
- **Восстановление по почте**: `POST /api/auth/forgot` кладёт временный ключ
  в `resets` на 30 минут и отправляет ссылку `/?reset=<ключ>` (`src/mail.js`).
  Пока `SMTP_HOST` не задан, ссылка пишется в лог: `docker compose logs app`.
  Смена пароля закрывает все прежние подключения.

### 4. Структурированное логирование

`src/logger.js` — pino, каждая запись строка JSON с полем `event`:
`http_request`, `login_failed`, `login_blocked`, `session_evicted`,
`access_denied`, `password_reset`, `unhandled_error` и т. д.

```
docker compose logs app | findstr login_failed
```

### 5. Автоматическая проверка кода

`.github/workflows/lab3.yml`: при каждом изменении в папке `lab3` GitHub ставит
зависимости (`npm ci`) и запускает ESLint (`npm run lint`). В репозитории этот
файл лежит в корне, рядом с папками лабораторных; в архиве приложен вместе с работой.
Те же правила лежат в `eslint.config.js`, локально — `npm run lint`.

## Как проверить вручную

Ключи доступа лежат в `localStorage`, а он **общий на весь браузер**. Поэтому
два пользователя одновременно — это два разных браузера или обычное окно плюс
приватное (Ctrl+Shift+N). В двух вкладках одного окна второй вход затирает первый.

1. **Роли.** Войти админом (`admin@lab3.local` / `admin12345`) → «Пользователи»
   → выдать второму аккаунту роль «Менеджер». Роль сервер каждый раз читает
   из базы, поэтому новые права действуют сразу — перезаходить не нужно,
   достаточно перейти на другой экран (шапка и список обновятся сами).
   - `user` видит в списке только свои задачи, у чужих нет кнопки «Удалить»;
   - `manager` видит все задачи (в карточке появляется почта владельца);
   - `admin` видит всё и раздел «Пользователи».
2. **Коды HTTP.** Открыть F12 → «Сеть» и посмотреть статусы: сохранение задачи
   с пустым названием — `422`, регистрация на занятую почту — `409`,
   заход в раздел админа обычным пользователем (`/api/admin/users`) — `403`,
   файл больше 10 МБ — `413`.
3. **Подбор пароля.** Пять раз ввести неверный пароль → шестая попытка даёт
   `429` и сообщение «Повторите через 15 мин». Снять блокировку раньше срока:
   `docker compose exec mongo mongosh lab3 --eval "db.attempts.deleteMany({})"`.
4. **Подключения.** Войти одним аккаунтом из трёх разных браузеров, затем из
   четвёртого — на экране «Подключения» останется три, самое старое закроется.
   Кнопка «Закрыть» у текущего подключения выкидывает из системы сразу.
5. **Восстановление пароля.** «Забыли пароль?» → указать почту → взять ссылку
   из лога: `docker compose logs app | findstr mail_skipped` → открыть её в
   браузере → задать новый пароль. Старая ссылка второй раз даёт `410`,
   все прежние подключения закрываются.
6. **Логи.** `docker compose logs app` — по строке JSON на каждый запрос.
7. **Проверка кода.** `npm run lint` локально; на GitHub — вкладка Actions
   после push.

Важно: `docker compose down -v` удаляет том с базой вместе со всеми
зарегистрированными пользователями и задачами. Чтобы просто перезапустить,
достаточно `docker compose restart` или `docker compose up -d --build`.
